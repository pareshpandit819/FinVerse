Overview

What is FinVerse?

A production-quality financial analytics platform that gives individuals a single, secure dashboard over all their financial accounts — with built-in intelligence for detection, forecasting, and advice.

📊 Aggregate

Unifies checking, savings, credit cards, investment accounts, and loans into a single dashboard with real-time net worth tracking.

🔍 Detect

Automatically identifies recurring subscriptions, spending anomalies, and budget overruns using rule-based and statistical algorithms.

🤖 Advise

Generates AI-powered health reports, spending forecasts, debt payoff strategies, and tax estimates via Claude Sonnet 4.6.

Core Problem Statement

Most individuals manage finances across 5–8 disconnected accounts with no holistic view. FinVerse replaces spreadsheets and app-switching with a unified analytical platform that surfaces insights automatically — reducing the cognitive load of financial management.

What Was Built · Part 2 of 3

Algorithms & Detection Logic

🔄 Recurring Transaction Detector

Groups last 90 days of transactions by normalized merchant name. For each group with ≥2 charges, computes average amount and checks:

maxDeviation = max(|aᵢ − avg| / avg)
if maxDeviation ≤ 0.10 → RECURRING
monthlyCost = (avg × 30) / (90 / count)

Detected 8 subscriptions in demo data. Exposed both in the web API and as a Claude tool for AI insights.

📉 Debt Amortization Calculator

Client-side real-time amortization — no API round-trip required:

while balance > 0 and months < 600:
  interest = balance × (APR/12)
  balance += interest − payment
  months++

Slider drag triggers recalculation in <1ms. Compares minimum-payment vs accelerated scenarios in real time.

📊 Spending Forecast (Linear Regression)

Aggregates 90 days of expense transactions into daily buckets. Computes:

mean = Σ(dailyAmount) / n
trend = (recent30Avg − older30Avg) / older30Avg
projection[i] = recent30Avg × (1 + trend × i/30)
confidence = 1 − (σ/mean) [clamped 0.3–0.95]

Persisted to SpendingForecast table with confidence score, upper/lower bounds, and methodology tag.

🧾 Tax Estimation Engine

2024 federal progressive brackets + 22 state flat-rate approximations. Long-term capital gains stacked on ordinary income to find the marginal LTCG rate:

taxableIncome = gross − stdDeduction
federalTax = bracketTax(taxableIncome)
ltcgTax = bracketTax(income+gains) − bracketTax(income)
stateTax = taxableIncome × stateRate

All calculation runs on the client — no server latency. Pre-fills income and gains from live Prisma queries.

Lessons Learned · Part 1 of 2

Technical Lessons

1
Prisma Schema ≠ Generated Client
Adding a field (e.g., subtype or forecastType @map("forecast_type")) to the schema requires three coordinated steps: run a migration, regenerate the client, and restart the server. Skipping any step produces silent P2022 column-not-found errors at runtime — not at compile time. This taught me that schema-first development demands a strict change management discipline.
2
pnpm Workspaces Have Non-Obvious Resolution Rules
In a monorepo, each package resolves dependencies from its own node_modules first. The Prisma client generated at the workspace root wasn't visible to sub-packages using a local stub, causing TypeScript and runtime divergence. The fix required either a custom output path or an explicit symlink — non-obvious without deep knowledge of pnpm's hoisting strategy.
3
JSON Cannot Serialize BigInt or Prisma Decimal
JSON.stringify() throws on BigInt and silently coerces Prisma Decimal objects to strings. Every API route boundary required explicit Number() and centsToDollars() conversions — a systematic issue that surfaced in 6 different routes. Naming all money fields *Cents in the shared types layer would have caught this earlier.
4
Browser Session State Outlives Database Resets
After a db:reset, existing JWT cookies in the browser still validate (same AUTH_SECRET) but reference stale user UUIDs. The dashboard resolved no organization membership and silently redirect-looped. The fix: clear the session before re-authenticating, and redirect to signout (not login) when org lookup fails.
5
Zod Validator Chaining Order Matters
z.number().default(90).min(30) throws at module load time — .default() returns a ZodDefault, not a ZodNumber, so .min() is undefined. The correct order is z.number().min(30).max(365).default(90). This crashed the forecast route on every cold start — a module-level error that blocked all 500 diagnostics.
6
Client Components Need Explicit Dep Arrays
Several useEffect hooks fetched data on mount with [] dependencies while using props (like organizationId) that were set asynchronously. Race conditions meant the component sometimes rendered with stale data. Splitting into two effects — one for orgId, one for data — resolved the ordering guarantee.

Lessons Learned · Part 2 of 2

Design, Product & Architecture Lessons

A
Seed Data Is a First-Class Feature
Early prototypes failed demos because analytical features (heatmap, recurring, forecasting) require dense, realistic data to be meaningful. A sparse or uniform seed gives no visual payoff. The final seed contains 99 transactions deliberately designed to create heatmap peaks, 8 recurring subscriptions, a 192% budget spike, and a 12-month net worth uptrend — all chosen to tell a story.
B
Progressive Disclosure Beats Feature Dumping
Early versions crammed all debt details into a single scrollable card with a separate dialog for strategy generation. Users had to navigate away to see results. The redesign — summary KPIs at top, per-debt cards with expand/collapse, inline slider calculator — kept everything in one mental context, dramatically reducing cognitive load during the demo.
C
Design Systems Pay Compound Interest
The first 4 modules were built with generic shadcn defaults (text-muted-foreground, bg-muted). When a unified sky-950 design system was applied, each subsequent module took ~40% less time to style because every decision (color, radius, shadow, spacing) was already resolved. Token-first thinking is not premature abstraction — it's prerequisite infrastructure.
D
Client-Side Computation Beats API Latency for Interactive Tools
The debt amortization slider and tax estimator originally made API calls on every input change. The latency (even at 50ms) made sliders feel laggy. Moving the math entirely to the client — pure JavaScript functions run in <1ms — made both features feel instantaneous. The only server call needed is the initial data fetch.
E
Error Surfaces Should Diagnose, Not Just Report
The forecast route returned generic 500s for weeks. Adding try/catch with console.error and propagating the actual error message to the client immediately revealed the Zod chaining bug. Opaque 500 responses are debugging debt — investing 15 minutes in structured error handling saves hours of diagnostics.
F
Architecture Decisions Have Long Shadows
The decision to store all monetary values as integer cents (BigInt) prevented all floating-point precision bugs but required explicit conversion at every JSON boundary. The decision to use a pnpm monorepo enabled shared code but added Prisma resolution complexity. Each tradeoff compounded — early decisions should be treated as load-bearing walls.

Breaking Points
🔴 Full-Table Scans for Recurring Detection
The current 90-day merchant grouping query requires scanning every transaction row for the org. At 5B rows this is a table scan disaster — no index helps a GROUP BY merchantName across partitions.
🟡 Budget Aggregation on Every Page Load
Budget spent amounts are read from the BudgetCategory table which is updated by a background job. At scale, this job queue cannot keep pace with real-time transaction ingest without pre-aggregated materialized views.
🔵 Per-User AI Insight Generation
Each health report calls Claude with ~3,000 input tokens. At 10M users generating weekly reports: 1.56T tokens/year — approximately $2M at current API pricing. Requires batching, caching, and model distillation strategies.
🟣 Synchronous Forecast Computation
Linear regression over 90 days of daily data is computed on-demand per request. At scale, forecasts must be pre-computed in batch overnight and cached — not recomputed per page load.

Big Data Analysis · Part 2 of 3

Infrastructure Solutions at Scale

Data Processing Pipeline

Apache Kafka — Real-Time Event Streaming
Transaction events published to finverse.transactions topic. Alert rule evaluation, budget aggregation, and anomaly detection subscribe as independent consumer groups. Eliminates the polling-based BullMQ approach that can't sustain millions of concurrent users.
Apache Spark — Batch Analytics
Nightly Spark jobs process the full transaction corpus: recurring detection as a distributed GroupBy, spending pattern clustering via k-means, and forecast pre-computation via distributed linear regression across partitioned user data. Replaces the synchronous per-request computations.
Data Warehouse (Snowflake / BigQuery)
Separate OLAP tier from the PostgreSQL OLTP. Transaction history, net worth snapshots, and portfolio valuations land in columnar storage optimized for aggregation queries. The dashboard reads pre-aggregated summary tables — not live transaction rows.
Delta Lake / Parquet — Time-Series Storage
Net worth snapshots and daily portfolio valuations stored in Parquet partitioned by (user_id, year, month). ACID transactions via Delta Lake protocol enable point-in-time queries without full scans. Reduces net worth history queries from O(rows) to O(partitions).

Caching & Serving Strategy

Redis Distributed Cache
Pre-computed results stored with TTL: budget aggregations (5 min), recurring subscriptions (24 hr), forecast data (12 hr), net worth snapshots (1 hr). Cache invalidation triggered via Kafka events on new transaction ingest.
PostgreSQL Read Replicas
The OLTP layer scales reads via streaming replication. Write operations (new transactions, goal updates) go to the primary. Dashboard reads, portfolio queries, and credit lookups route to read replicas — eliminating read/write contention.
Materialized Views for Aggregations
Budget category spending, monthly net worth, and per-category transaction totals pre-computed as PostgreSQL materialized views. Refreshed incrementally on transaction insert via Kafka consumer — not on every page load.
AI Cost Optimization
Embed user spending patterns as 768-dim vectors (via smaller embedding model). Batch similar users together. Use Claude only for final narrative generation on pre-computed numerical summaries — reducing per-user token consumption by ~80%.

Big Data Analysis · Part 3 of 3

Transformative Opportunities at Population Scale

Big data doesn't just solve the scaling problem — it enables entirely new product capabilities impossible with single-user data.

🏘️

Peer Benchmarking

"Your food spending ($509/mo) is 34% above households with similar income in your metro area." Cross-user analytics (privacy-preserving via k-anonymity / differential privacy) transforms individual dashboards into contextualized intelligence.

Requires: Spark aggregations + census cohort modeling
🔍

ML Fraud Detection

Isolation Forest over transaction vectors (merchant, amount, time, location) trained on 5B+ labeled transactions. Detects anomalous charges in real time — a feature impossible without population-scale training data.

Requires: Kafka streams + model serving (Seldon/BentoML)
📉

Predictive Credit Modeling

Feature engineer 40+ signals from spending patterns, payment timing, and balance trajectories. Train gradient boosted classifier to predict credit score change 60 days in advance — actionable, not retrospective.

Requires: Feature store + XGBoost pipeline
📊

Market Correlation Engine

Correlate portfolio holdings with macro indicators (CPI, Fed rate decisions, sector ETF flows). When SPY drops 3%, proactively surface "Your NVDA position is correlated at 0.84 with NASDAQ — consider rebalancing."

Requires: Time-series DB + financial data APIs
🤖

Personalized AI Distillation

Fine-tune a smaller model (Haiku-class) on FinVerse-specific financial reasoning using RLHF from user feedback signals on insight cards. Reduces inference cost by 10× vs Claude Sonnet while maintaining domain accuracy.

Requires: SFT pipeline + feedback telemetry
🔔

Proactive Alert Intelligence

Current alerts are rule-based thresholds. With population data, alerts become ML-driven: "Your gym membership ($25) has been unused for 47 days — 89% of users in this situation cancel within 60 days. Act now?"

Requires: Behavioral cohort analysis + Kafka streaming
